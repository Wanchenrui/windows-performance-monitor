# v0.7.2 可选特权 Broker

## 进程与数据层级

```text
PerfMonitor.Desktop（当前用户，非提权）
  │ typed action DTO
  ▼
PerfMonitor.Agent（当前用户，非提权）
  ├─ 用户策略：只可收紧
  ├─ 生成 idempotencyKey / deadline
  └─ Broker client
       │ global local Named Pipe
       ▼
PerfMonitor.Broker（Windows 服务，LocalSystem）
  ├─ 从 Pipe 取得 SID/PID/映像，不信任 body
  ├─ 机器策略：调用者、映像、动作、目标
  ├─ SQLite audit + idempotency
  └─ 单一 OS executor
```

监控数据仍按既有路径流动。Broker 不读取 Provider 快照、不写用户历史库，
也不被 Provider scheduler、诊断队列或 IPC subscription 等待。

## 一次动作

```text
Desktop typed request
  -> Agent 结构/用户策略校验
  -> Broker transport identity
  -> Broker DTO/机器策略/目标不变量校验
  -> INSERT pending + COMMIT
  -> capture before
  -> dry-run ? return planned : execute one typed OS operation
  -> capture after
  -> UPDATE terminal + COMMIT
  -> Agent -> Desktop
```

设规范化请求为 \(R\)，实际调用者 SID 为 \(S\)，幂等键为 \(K\)，请求
摘要为：

\[
H = \operatorname{SHA256}(
  \operatorname{UTF8}(\operatorname{CanonicalJson}(R)))
\]

持久化唯一键是 \((S,K)\)。只有记录不存在时才能创建 `pending`。已有
记录的决策为：

\[
f(S,K,H)=
\begin{cases}
\mathrm{ReplayStoredResult}, & H=H_0 \land state\in Terminal\\
\mathrm{Indeterminate}, & H=H_0 \land state\in\{pending,indeterminate\}\\
\mathrm{Conflict}, & H\ne H_0
\end{cases}
\]

这里的 “Replay” 只重发已存结果，不再次调用 executor。

## 动作 DTO

| 动作 | 请求参数 | Broker 再校验 | 执行后状态 |
|---|---|---|---|
| SetProcessPriority | PID、creation ticks、优先级枚举 | 同 SID、非保护目标、允许枚举 | PID、creation ticks、实际优先级 |
| TerminateProcess | PID、creation ticks | 同 SID、非保护目标、策略允许 | 已退出/仍运行及稳定结果 |
| StartApprovedDiagnostic | diagnostic ID | ID 存在且机器策略启用 | 新 PID/启动时间或拒绝码 |
| ApplyApprovedPowerProfile | profile ID | ID 映射到已批准 GUID | 修改前/后活动 profile ID |

请求中不存在可执行路径、命令行、工作目录、环境变量、脚本、注册表路径或
任意 GUID。

## 进程身份与 PID 复用

进程动作使用：

\[
I_p=(PID,\ CreationTimeTicks,\ OwnerSid)
\]

Desktop/Agent 看到的 `(PID, creationTimeTicks)` 只是候选目标。Broker 在
动作临界区重新读取三元组，并要求创建时间和传输层 SID 同时相等。即使
原进程在请求传输期间退出且 PID 被复用，新进程也不会被修改。

## 故障状态机

```text
received
  ├─ malformed / unsupported ──────────────► rejected
  ├─ caller/image/policy denied ───────────► denied
  ├─ idempotency conflict ─────────────────► conflict
  ├─ previous pending ─────────────────────► indeterminate
  └─ pending committed
       ├─ dry-run ─────────────────────────► dry_run
       ├─ target changed before execute ───► rejected
       ├─ executor stable failure ─────────► failed
       ├─ executor success + audit commit ─► succeeded
       └─ crash/unknown completion ────────► pending
             next startup ─────────────────► indeterminate
```

审计数据库在 `pending` 提交前失败时，executor 不会被调用。executor 之后
的提交失败会保留或恢复为 `indeterminate`；调用方不得把超时等同于失败并
自动重试。

## 服务与开发模式

- `--service`：只在 LocalSystem 下运行，启用机器策略允许的真实动作；
- `--console`：用于开发和 CI，强制 dry-run，不允许真实 executor；
- Broker 未安装：Agent capability 报告 unavailable，其他产品功能不变。

服务安装、ProgramData ACL、Agent 映像固定和升级切换由 v1.0 安装门禁
完成。v0.7.2 的可执行文件、协议、策略和审计实现先在隔离测试中冻结。

## 验收门槛

- 协议正常、超大、截断、未知动作和额外执行字段测试；
- 实际 Pipe SID/PID 身份注入测试，请求体无法伪造 caller；
- PID 创建时间、所有者和保护进程拒绝测试；
- Agent policy 与 Broker policy 任一拒绝即不调用 executor；
- dry-run 对四类动作均不修改状态；
- 相同幂等键只调用 executor 一次，请求摘要冲突被拒绝；
- 模拟 `pending` 崩溃后恢复为 `indeterminate` 且不重放；
- before/after/拒绝/失败审计完整性测试；
- Broker 缺失或崩溃不影响采样、SQLite 历史或 Desktop 只读路径；
- 测试只使用 fake OS executor，CI 不终止真实进程、不改优先级或电源计划。
