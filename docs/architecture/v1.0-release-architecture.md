# v1.0 发布架构与验收门禁

## 交付拓扑

```text
signed PerfMonitor-1.0.0-win-x64.msi
  ├─ Core（必选）
  │   ├─ signed Agent
  │   ├─ signed Desktop
  │   ├─ signed Provider Worker
  │   ├─ signed support/recovery tool
  │   ├─ Common Startup Agent shortcut
  │   └─ Start Menu Desktop shortcut
  └─ Broker（默认不选）
      ├─ signed Broker
      ├─ LocalSystem service
      └─ protected ProgramData policy/audit directory

release metadata
  ├─ pre-sign build manifest
  ├─ final signed-file release manifest
  ├─ CycloneDX SBOM
  ├─ vulnerability reports
  ├─ detached-CMS signed update manifest
  └─ GitHub artifact attestations
```

安装器只改变部署层，不把 Desktop 或 Agent 提权。Agent 仍在交互用户会话
中运行；Broker 仍是唯一允许执行白名单机器动作的边界。

## 候选状态机

```text
source commit
  -> locked restore + tests
  -> publish win-x64
  -> pre-sign build manifest
  -> Authenticode sign executables
  -> verify signer/mode
  -> build MSI
  -> Authenticode sign MSI
  -> install/upgrade/rollback/uninstall matrix
  -> attest four-target support-matrix evidence
  -> crash/migration/resource/privacy/Broker gates
  -> SBOM + vulnerability reports
  -> signed update manifest
  -> final release manifest
  -> provenance attestations
  -> release candidate
```

任一步失败都使候选失效。不能在签名后替换二进制，也不能在生成 update
manifest 后替换 MSI 或 SBOM。

## 签名模式

| 模式 | 证书 | 时间戳 | 可发布 |
|---|---|---|---|
| local unsigned | 无 | 无 | 否，仅开发构建 |
| CI test | 短期自签 Code Signing | 禁止冒充生产 | 否 |
| production | 配置的发布证书，链/主体/指纹通过 | RFC 3161 | 是 |

所有证据显式保存 `signatureMode`。生产脚本遇到自签证书、缺失时间戳 URL、
主体/指纹不匹配或未签文件时必须非零退出。

Broker 的运行期调用端校验与发布时签名校验是两道独立门禁。LocalSystem
Broker 对实际 Pipe 客户端映像解析最终路径、计算文件 SHA-256，并用
WinVerifyTrust 验证信任链和 Code Signing EKU；随后按机器策略同时固定
Agent 的 Program Files 路径、发布者 Subject 和证书 SHA-256。service
模式不能关闭这些条件，且验证禁用网络 URL retrieval，因此不会把证书网络
响应时间耦合进 Agent 采样路径。

## 安装生命周期验收

全生命周期测试至少覆盖：

1. 干净安装 Core，确认 Broker 未安装；
2. 登录用户启动 Agent，Desktop 能连接，SQLite 能写入；
3. Modify 安装 Broker，确认服务账户/路径/启动和 ACL；
4. 从上一候选升级到 1.0，用户库与 Broker 审计保留；
5. 默认直接降级被阻止；
6. 受控回滚：卸载 1.0、安装上一签名候选、旧 schema 可读；
7. 卸载产品后程序、快捷方式和服务消失，数据按策略保留；
8. 重新安装后可继续使用保留数据；
9. 重复安装/修复不创建重复启动项或服务。

CI 的安装证书是受本机临时根信任的测试证书。该测试只能证明 MSI/签名和
生命周期机制，不能证明最终商业发布者的公信链。

## 数据恢复验收

- 在持续写入 SQLite/WAL 时强制终止 Agent；
- 重新启动并要求 `integrity_check=ok`；
- 断电前已提交序列仍可查询，未提交事务不出现半行；
- schema 1 升级前 backup 的 hash、schema 和完整性可验证；
- 注入 migration 失败后原库仍为 schema 1；
- schema 2 backup 恢复必须拒绝冒充 schema 1；
- 旧二进制面对更高 schema 只能只读降级/拒绝，不能写入。

## 资源公式

对稳态样本 \(x_i\)：

\[
\mathrm{CPU}_{core\%}
=100\cdot
\frac{CPU(t_n)-CPU(t_0)}{t_n-t_0}
\]

\[
\mathrm{RetainedGrowth}
=\operatorname{median}(\mathrm{tail}_{20\%})
-\operatorname{median}(\mathrm{head}_{20\%})
\]

门禁同时检查 peak、retained growth、GC growth、handle peak、首尾
20% handle 中位数增长和 thread peak。只有所有指标小于等于
`release/resource-budgets-v1.json` 才通过。句柄增长定义为：

\[
\mathrm{RetainedHandleGrowth}
=\operatorname{median}(\mathrm{tail}_{20\%})
-\operatorname{median}(\mathrm{head}_{20\%})
\]

生产门禁不能只信任 soak JSON 中的 `passed`。它必须重新按冻结预算比较
全部数值，并把 72 小时证据中的 `productVersion`、`agentSha256` 与
`release/evidence/v0.4-agent-baseline-candidate.json` 固定的源分支 head、
CI run、artifact digest 和 Agent digest 绑定；该 head 还必须是当前发布
commit 的祖先。候选固定的快照/探针周期用于推导最低覆盖数，避免进程
存活但采样停滞仍通过。候选描述和实测证据都进入最终 release manifest
的文件摘要。

## 供应链验收

- NuGet locked restore；
- `.NET` 使用 NuGet advisory 数据扫描 direct/transitive dependency；
- Python 的 Windows x64/CPython 3.12 direct/transitive wheel 均固定版本与
  SHA-256，并以 `--require-hashes --only-binary=:all:` 安装；独立且同样
  hash-locked 的 `pip-audit` 环境扫描 requirements；
- CycloneDX SBOM 包含 NuGet、Python oracle、WiX 和最终文件摘要；
- pre-sign build manifest 保存 commit、toolchain、依赖输入和未签名
  product file SHA-256，并明确不可发布；
- final release manifest 重新校验并绑定所有已签名 product file、MSI、
  SBOM、漏洞输入、四目标支持矩阵、门禁证据和签名者；
- GitHub `actions/attest` 绑定最终 MSI/update manifest/SBOM 与 workflow
  identity。

支持矩阵是独立的两阶段门禁。第一阶段从受保护的 `main`/`v1.0.0`
commit 只构建一次 test-signed MSI，并把同一 MSI 分发到 Windows 11
24H2、Windows 11 25H2、Windows Server 2022 Desktop Experience 和
Windows Server 2025 Desktop Experience 专用 runner。每台主机在任何
安装写入前先从注册表验证 build、`InstallationType` 和 x64 架构，再执行
安装生命周期。第二阶段聚合四份证据并建立 OIDC attestation。production
workflow 只接受同仓库、指定 workflow、相同 commit 且成功 run 的 attested
evidence。

漏洞门禁不允许“扫描失败当作没有漏洞”。无法访问 advisory source、JSON
无法解析或 scanner 非零异常均 fail closed。临时豁免必须是仓库内有
到期时间、CVE、影响分析和 owner 的审查文件；v1.0 初始为空。

## 完成定义

代码、文档和测试就绪不等于正式发布。完成必须有：

- v1.0 分支精确 head；
- 本地全量门禁；
- GitHub 精确 run/job/artifact/attestation 证据；
- 真实 v0.4 72 小时基线通过；
- 按顺序合并所有堆叠版本；
- 每个版本 tag 与 GitHub/local main 同步；
- 生产发布时另有真实发布证书证据；若证书未配置，只能冻结为经过测试签名
  的 release architecture，不能声称已经获得受信任发布者签名。
