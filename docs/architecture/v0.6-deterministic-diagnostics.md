# v0.6 确定性诊断实现说明

## 数据流与时序

```text
immutable snapshot
  ├─ TryWrite -> SQLite work queue (capacity 256)
  ├─ TryWrite -> diagnostic queue (capacity 256)
  │              single evaluator
  │                ├─ bounded recent RAM list (2,000)
  │                └─ TryWrite event -> same SQLite work queue
  └─ TryWrite -> IPC latest-wins subscription
```

所有 `TryWrite` 都在调用线程立即返回。诊断和 SQLite 的最坏 I/O 时间不进入
Provider deadline。诊断 sink 失败只增加失败计数；实时规则状态继续推进。

## 规则状态机

规则输入先由 metric group 读取器验证 availability、JSON 类型、有限数值和
单位，再产生统一 observation。重复或逆序时间被忽略；超过连续性上限会
清除 pending debounce 和旧证据，但不会凭缺失数据自动解除活动告警。

`active` 与 `resolved` 是唯一输出状态。每次输出包含实际策略的阈值描述、
激活/恢复 debounce、cooldown 和最近证据，因此修改默认阈值不会改变旧
事件的解释。满足完整 debounce 后 confidence 固定为 1。

## 七类首批规则

| 规则 | 默认激活 | 默认恢复 | 激活/恢复 debounce |
|---|---|---|---:|
| high CPU | CPU ≥ 90% | CPU ≤ 75% | 30 s / 30 s |
| memory pressure | 内存 ≥ 90% | 内存 ≤ 80% | 30 s / 30 s |
| system disk low | 系统卷使用 ≥ 90% | ≤ 85% | 60 s / 60 s |
| configured process spike | 归一化 CPU ≥ 80% | ≤ 50% | 20 s / 20 s |
| sampling gap | 相邻逻辑样本 ≥ 5 s | ≤ 2 s | 0 s / 6 s |
| provider unavailable | 持续不可用 | 持续可用 | 120 s / 30 s |
| Agent resource anomaly | CPU ≥ 20% 核心等效或 private ≥ 256 MiB | CPU ≤ 10% 且 private ≤ 192 MiB | 60 s / 60 s |

这些数值是默认产品策略，不是硬件规格。进程规则只有显式配置 watchlist 后
才启用具体主体。

## SQLite schema v2

诊断事件通过 `StorageWorkItem` 与快照共用单 reader/writer channel。事件
ID 有唯一约束，重复投递幂等。索引覆盖 lastSeen、rule/time 与 state/time；
查询范围最多 366 天、2,000 条。v1 的预留表重命名为
`diagnostic_events_v1`，避免静默丢弃潜在旧数据。

## 历史重放

raw snapshot 查询先计数再流式读取，超过 48 小时或 200,000 条直接拒绝，
不返回截断的“近似重放”。顺序固定为
`sample_time_ms, instance_id, sequence`。测试将在线 evaluator 的事件 JSON
与 SQLite raw 历史重放 JSON 做精确比较。

## 无动作约束

Desktop 的“查询诊断”只读最近事件。v0.6 没有修复按钮，Named Pipe 没有
执行型 DTO，capabilities 明确 `actionsSupported=false`。诊断证据不包含
命令行、脚本、注册表、完整路径或 PID；配置进程仅保留经校验的进程名。
